Many cities publish their service requests (potholes, rodents, noise) as open data, free and without a key, through an
API that answers 1,000 records a page. This recipe reads one week's worth into a pipeline, five pages at most, counts
the requests per ward and keeps the counts for a community-health board. It is also the shortest way to learn API
collections and paging: one collection, one request, one **Read API** step.

> **Note:** The data comes live from a public portal, so your counts differ from day to day. This recipe uses the City
> of Chicago's portal, as Summit Valley's does; any portal on the same software (Socrata) works with its own address.

## What you'll build

- An API collection **Open data** with an environment that holds the portal's address, and one request **Chicago: 311
  service requests** that pages by offset.
- A pipeline **City open data: 311 complaints** of three steps and a weekly schedule.

![The run's steps](rcp-x-311-run "Summit Valley's run: 5,000 service requests over five pages, 51 wards")

## What you need first

1. Page access to **API collections** and **Pipelines**, as a workspace administrator.
2. **A storage connection**, *your bucket* (see [Connect your storage](#con-storage)).
3. The platform must be allowed to call `data.cityofchicago.org`; public addresses usually are (see
   [What the console may call](#con-addresses)).

No sample file: the data is the portal's.

## Build it

### The collection and its request

1. **Get data in › Connections › API collections**, **New collection**. **Name** `Open data`; **Sensitivity**
   **Public**; under **Default auth** the **Scheme** **None** (the portal needs no key). **Create** (see [Make an API collection](#con-api-collections)).
2. Under **Environments**, **New environment**, name it `Open data`, tick **Default**, and add the variable
   `chicagoBase` = `https://data.cityofchicago.org/resource`. **Create**.
3. Choose **Add API**: **Method** `GET`, **URL** `{{chicagoBase}}/v6vf-nfxy.json`, **Name** `Chicago: 311 service
   requests`.
4. On **Params**, add `$where` = `sr_type like '%Rodent%'` and `$order` = `created_date DESC`.
5. On **Settings**, **Paging** **Offset**: **Offset parameter** `$offset`, **First offset** `0`, **Size parameter**
   `$limit`, **Page size** `1000`, **Items at** `$`, **Most pages** `5` (see [Page through results](#con-api-paging)).
6. Choose **Save & test**. The test's line reads "5000 items over 5 pages", and may add that it stopped at the page cap
   with more to fetch: that is expected, five pages is the limit you set.

```The request's address
{{chicagoBase}}/v6vf-nfxy.json
```

### The pipeline

1. **Build › Pipelines › New pipeline**, **Add steps yourself**, **Name** `City open data: 311 complaints`, **Create
   and add steps**.
2. Add:

| # | Step | Key | Settings |
|---|---|---|---|
| 1 | Read API | `sr` | **API request** `Chicago: 311 service requests`; **Columns**: `ward` as `ward`, `sr_type` as `sr_type`, `created_date` as `created`; **At most rows** `5000` |
| 2 | Aggregate | `by` | **Group by** `ward`; **Aggregations** `count` as `requests` |
| 3 | Upload to bucket | `keep` | **Bucket** your bucket; **Object key** `open/311/by-ward.csv`; **Format** `csv` |

3. **Settings**: **Data sensitivity** **Public**. **Validate**, **Save**.
4. **Schedule**: **On a timetable**, **Weekly**, every 1 week at `06:00` **On these days** Wed. **Create schedule**,
   then **Run now**.

## Check it worked

The run is **Completed**, 3 of 3 steps: **Read API** 0 → 5,000 (five pages of 1,000), **Aggregate** 5,000 → about 50
(one row per ward, and one for requests with no ward), **Upload to bucket** the same rows. The step takes some seconds:
it waits for five pages from the portal.

Open `open/311/by-ward.csv` in **See results › Analysis › Files**: two columns, `ward` and `requests`. A pipeline or a
dashboard reads it from there.

Summit Valley's run read 5,000 requests in about 26 seconds and counted 51 wards.

## Common mistakes

- **Only 1,000 rows come back.** The request has no **Paging**, or **Most pages** is 1. Paging is the request's own
  setting, not the step's.
- **The test answers 400.** A parameter is misspelt: the portal's names start with `$` (`$limit`, `$offset`, `$where`).
- **The address is refused.** The host is not on the platform's list of addresses it may call; ask your account team
  (see [What the console may call](#con-addresses)).
- **The columns are empty.** **From the row at** is the field's name in the portal's answer, exactly: `sr_type`,
  `created_date`, `ward`.
